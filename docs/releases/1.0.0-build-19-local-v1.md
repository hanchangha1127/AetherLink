## Android Backup And Device-Transfer Contract

Build 19 retains `android:allowBackup="false"`. The packaged values are
`allowBackup=false`, `dataExtractionRules=@xml/data_extraction_rules`, and
`fullBackupContent=@xml/backup_rules`.

The legacy full-backup resource excludes `root`, `file`, `database`,
`sharedpref`, and `external`, each with `path="."`. The Android 12+ resource
contains exactly `cloud-backup` and `device-transfer`; each section excludes
those five domains plus `device_root`, `device_file`, `device_database`, and
`device_sharedpref`, again with `path="."`. No `<include>` rule is present.

The builder and independent checker bind the APK manifest fields to the
packaged resources and parse the compiled policy bodies. For the AAB, they
require `bundletool validate`, inspect the base manifest, materialize a
temporary AAB-derived universal APK, and apply the same compiled XML body
checks. Temporary readback signing material is local to the inspection
directory and is not a production signing identity.

The exact tools are `aapt2 dump xmltree + resources --no-values` and
`bundletool dump manifest`.

Build 15 is the first local release that requires both APK and AAB
backup-policy manifest readback. Build 17 adds compiled XML body readback for
both the APK and an AAB-derived universal APK. Build 19 retains that
packaged-policy contract. This evidence does not claim that an Android vendor,
cloud service, or physical device performed backup or transfer.

## Runtime-Chat SQLite Contention And Cross-Process QA

The production Runtime-chat SQLite store configures a five-second
(5,000-millisecond) busy timeout on every opened database connection. SQLite
`BUSY` and `LOCKED`
results, including extended result codes, resolve to the stable user-facing
message `Runtime chat history is temporarily busy. Try again.` without a
database path or raw SQLite lock text.

Three deterministic Swift tests control transaction progress with explicit
wait points around `BEGIN IMMEDIATE`, writes, and `COMMIT`:

- a second store instance waits for the first writer and then commits its
  event exactly once;
- a writer held beyond five seconds fails with the stable busy message, leaves
  no contender event or FTS row, and a later reopened store succeeds;
- a read transaction that blocks `COMMIT` forces rollback of both the event
  and FTS row before the same event succeeds after reopen.

Those three deterministic wait/`BEGIN`/`COMMIT` tests are included within the
passing 90/90 `SQLiteRuntimeChatEventStoreTests` suite.
